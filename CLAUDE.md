# rvrs CLI

The `rvrs` binary for macOS and Linux (Rust 2021, no async runtime): the network tools engineers already type, with their flags, plus what the rvrs app does. traceroute, ping, MTR, dig and BGP are the tools today; iperf3 is next. The same binary later runs as a node (`rvrs node`). Sibling repos: `../ios-app` (the iOS app, whose Swift engine and models this ports; its `WORLDVIEW.md` says where rvrs is going and `docs/tasks/cli-bootstrap.md` is this repo's plan), `../app` (the API; runs, accounts and nodes land there).

- State-of-the-art ease of use, in the spirit of gh, minikube and k9s. Nothing to set up, good help, color, completion, plain errors that name the next step.

- Keep README.md, `docs/` and this file current with every change. The README is short on purpose (the user's call, 2026-11-20: "really EASY to digest"): what rvrs is, the tools, install, using it in place of the originals, privacy and links. Flags, keys, the report, files and every request rvrs makes live in `docs/` (one file per tool, `console.md`, `commands.md`, `privacy.md`). No sentence in the README explains how the installer or the binary works inside.
- **Releases** (2026-11-20, the user's go): `.github/workflows/release.yml` runs on a tag `v<VERSION>.<patch>` that matches the commit's computed version, or from Actions > Release > Run workflow, which tags the newest `main`. It builds `aarch64`/`x86_64-apple-darwin` on macos-latest, `x86_64`/`aarch64-unknown-linux-musl` on Ubuntu runners (musl-gcc) and `armv7-unknown-linux-musleabihf` on Ubuntu with `gcc-arm-linux-gnueabihf` (checked under `qemu-arm`), each twice through `scripts/build.sh`: the small build without the Console, then the full build (see Build features). It packs `rvrs-<target>.tar.gz` and `rvrs-<target>-without-console.tar.gz`, builds a `.deb` (cargo-deb) and an `.rpm` (cargo-generate-rpm) of the full build for x86_64 and arm64 Linux, writes `SHA256SUMS`, and publishes them with `install.sh` as a GitHub release. `rvrs-<target>.tar.gz` is the full build under the name every rvrs from before build features updates from, so it keeps that name for good. The `homebrew` job writes `Formula/rvrs.rb` into `rvrs-dev/homebrew-tap` with `scripts/formula.sh`; it needs the secret `TAP_TOKEN` (a token that can push to the tap) and skips with a line when it's missing. `.github/workflows/ci.yml` runs fmt, clippy and the tests on macOS and Linux for every push and pull request. `rvrs update` and `install.sh` both check the archive against `SHA256SUMS`. A binary in `/usr/bin` is a package (`Install::Package`) and `rvrs update` leaves it to the package manager.
- `install.sh` is the installer the site serves as `rvrs.dev/install.sh` (README, Install), a redirect to the newest release's `install.sh`. On a terminal it asks per tool whether rvrs should run as traceroute, ping, mtr and dig (default no, reading answers from `/dev/tty` so it works under `curl | sh`) and whether to set up completion for the shell in `$SHELL` (default yes); `--link`, `--no-link` and `--yes` answer for it, and without a terminal it asks nothing, links nothing and sets up nothing. `--without <build features>` leaves build features out (see Build features); by default it installs the full build. It reads the release's `SHA256SUMS` first, which says which builds the release has, and stops with a sentence naming them when there is none for the asked set. It downloads `rvrs-<target>[-without-<build features>].tar.gz` from the latest GitHub release (`x86_64`/`aarch64` on `apple-darwin`/`unknown-linux-musl`, and `armv7-unknown-linux-musleabihf` for `armv7l`, the archive holding `rvrs` at its top level), installs to `~/.local/bin` (`RVRS_INSTALL_DIR`), and links `traceroute`, `ping`, `mtr` and `dig` next to it when asked and when the build has that tool, never over a real file, then says when the links are shadowed on `PATH`. `RVRS_INSTALL_ARCHIVE=<file>` installs a local archive, which is how it is tested.

## How it works

- **Build features** (`features.rs`, initiative B1 in `../ios-app/docs/initiatives/small-build.md`, built 2026-11-22; the user's rules that day: every build and every update is the full build unless a person leaves something out, today's installs update as full builds, and a build feature added later is in by default; they said modules, and the glossary's word is build feature, with module in its Not column, which they kept on 2026-11-23). A build feature is a Cargo feature of the `rvrs` crate: `traceroute`, `ping`, `mtr`, `dns`, `bgp`, `tcp` and `mtu` (both inside traceroute, so leaving out traceroute leaves them out) and `console` (ratatui, which is optional). `default` has them all, on one line, because `scripts/build.sh`, `scripts/check-features.sh` and a checkout's `rvrs update` read it. The names are the node protocol's `features` (a test reads the heartbeat row), so they never change. `features::ALL` lists them with `cfg!` for whether this build has each. A build feature decides what a build can run, never what it can show: the dispatch in `main.rs` and `trace::run` (for `-T` and `--mtu`) refuse with `features::refuse` ("This build of rvrs leaves out BGP. rvrs update --with bgp adds it.", exit 1) behind `if !cfg!(feature = …)`, a constant, so the optimizer drops the command and the linker drops the engine in `rvrs-core` that only it calls. That is why `rvrs-core` has no features of its own: it stays whole and the binary decides what is reachable. The looks of every tool stay in every build, so `rvrs show`, history and the Console show every run; a build without the Console prints the help for `rvrs` alone and traces `rvrs <target>`. The Console offers only `features::runs(tool)` and toasts the refusal in `start_with`. `term::size` asks the terminal with `TIOCGWINSZ` itself, so only the Console uses crossterm. `rvrs status` has a Build features line and a Left out line, `rvrs --version` ends with "without console", and `help::main` shows Usage for what the build runs and tags left-out tools and flags Left out. What a build remembers is what it leaves out (`features::left_out`), and `rvrs update` asks for the build that leaves out the same (`features::wanted`, with `--with` and `--without` to change it), named by `features::archive`: `rvrs-<target>.tar.gz` for the full build, `rvrs-<target>-without-<sorted names>.tar.gz` otherwise. A binary update reads `SHA256SUMS` first and stops when the release lacks that archive (`no_such_build`), never putting a bigger build on a router unasked. A checkout builds `-p rvrs --no-default-features --features` from the pulled Cargo.toml's `default` less what it leaves out, and needs no remote to change build features. Homebrew and the packages are full builds and refuse `--with` and `--without` with the installer's command. The small build is the build without the Console with `[profile.small]` (`opt-level = "z"`, fat LTO): on 2026-11-22 it was 2.95 MB on aarch64 musl and 2.82 MB on ARMv7 against 5.1 MB for the full build, and the profile alone took a third off. CI (`small-build`) builds it for x86_64, aarch64 and ARMv7 musl, runs it, and fails over the budget in `scripts/small-build.budget` (3.5 MiB on the ARM targets, 4 MiB on x86_64, which measured 3.65 MB) or when a crate comes in or leaves that `scripts/small-build.deps` doesn't list; `features` builds without each one with warnings as errors. MIPS is a tier 3 target with no standard library from rustup, so ARMv7 is the first router target. Not done: `rvrs node` keeping runs in memory instead of a history file (with the node), and iperf3 as a build feature (when the CLI runs it).
- **Engine.** `engine::run` sends one probe to every hop per round, rounds back to back, 5 ms apart, on one thread that also reads replies. Probes are matched by echo sequence (a counter mapped to TTL and round, so up to 255 hops and 10 probes per hop). A reply from the destination stops probing beyond it. A probe's wait is `-w` until the destination has answered, then ten times the slowest reply, at least 500 ms. Events: `Sent`, `Reply`, `Lost`, `Finished`, `Failed`.
- **Ping.** `engine::ping` sends one echo request per interval at one TTL, matches replies by sequence, and calls a packet lost after `-W` (2 s by default). A router that answers instead of the target is a `PingRefused` and a `Slot::Refused`: sent, not received, and printed as ping prints it. A ping run keeps every packet in one hop (`Run::packets()`), as the app does. `Verdict::of(stats)` is the app's `ConnectionInsight`, thresholds and words. On a terminal each settled packet is printed once above a live region (`LiveRegion::print_above`) that holds the sparkline and the status line; the closing block puts the chips (`chips::line`: p50, p95, p99 and loss, PARITY.md's pattern 8) above the sparkline, then the figures and the verdict. The reply's TTL comes from the IPv4 header on macOS and from a control message (`IP_RECVTTL`, `IPV6_RECVHOPLIMIT`) elsewhere.
- **MTR.** `engine::mtr` is the traceroute engine paced: one probe to every hop per round, a round per interval (1 s; routers rate-limit their replies at anything much faster), until `-c` rounds or a stop. Rounds have no upper bound, so MTR has its own events (`MtrSent`, `MtrReply`, `MtrLost`, round as `u32`) and a hop grows a slot per round (`Run::mtr_slot`). A run keeps its newest `Run::MAX_ROUNDS` (1200) rounds: older ones are dropped from the front of every hop and `Run::first_round` counts them, as the app caps its samples. The first round probes up to `-m` to find the path at once; while the destination is unknown, later rounds stop `-U` (5) hops past the farthest hop that answered. The app's rules are ported word for word: `Run::chart_hop` (the destination, else the farthest hop that answered), `loss_carries` (loss at a middle hop counts only when the chart hop loses too), `rate_limited_hops` (two losses and 10%), `rate_limit_note` (the app's sentence, listed as `ListFormatter` lists), and the report adds the verdict on the destination and the note to `interpretation`. Loss is red only when it carries and gray otherwise, in both looks. `mtr::report_lines` is mtr's `-r` report, column for column (a loss of 100.0% takes a space from the host column, as mtr's does); a pipe, `-r`, `--classic` or an `mtr` symlink gets it, with 10 rounds when `-c` doesn't say. On a terminal `mtr::table` is redrawn in place: hops under their network, Loss, Snt, Last, Avg, Best, Worst, Jitter, and from about 150 columns a sparkline of each hop's newest rounds (`mtr::sparkline`, scaled to the slowest reply of the run). `-j` is the rvrs report, not mtr's JSON. In the Console an MTR runs until `s` (`App::mtr_lines`): the same figures with a ROUNDS strip, `d` for a wide strip of each hop's rounds (`mtr_history`; not "history", which the glossary keeps for stored runs), the chart hop's latency by round under the table, the selected hop's own chart in the details column, and Run MTR (`m`) among a hop's actions. The closing block puts the destination's chips (p50, p95, p99 and loss) between the summary and the rest of its figures. In the Console the chips (`chip_line` in `console.rs`) sit above every latency chart: under the chart hop's caption, above a hop's own charts in its details, and above a ping's LATENCY BY PACKET, whose tile row keeps SENT, LOSS, AVG, MIN, MAX and JITTER. Both draw from `chips::chips`, so they say the same (PARITY.md, pattern 8; 2026-11-26). Verified 2026-11-20 on macOS and in the Debian container, as root and as a normal user.
- **DNS.** Ported from the app's `Networking/DNS` and `Models/DNSResult.swift`, sentence for sentence (the user's ask, 2026-11-20: "feature parity with DIG and how we do DNS on the iphone"). `dns::message` builds and parses RFC 1035 messages with EDNS(0); a `Presentation` picks the app's short values or dig's zone-file values. `dns::client::query` asks over UDP and again over TCP when the answer is truncated. `dns::lookup::run` asks the device's resolver (the first `nameserver` in `/etc/resolv.conf`, labeled Router when private), Cloudflare, Google, Quad9 and any `--resolver` for nine types each on scoped threads, and walks the delegation from the root for the authoritative answer, DS at each parent, DNSKEY and RRSIG. It reports through `DnsEvent`, which `Run::apply_dns` folds into `Run.dns` (a `DnsResult`, stored with the run; older history files load without it). DNSSEC is presence only: say "signed", never "verified". `dns::result` holds the rules the screens share: `Diff` (notes with their usual reason, `status` per source), `verdict`, `headline`, `summary`, `changes` against `History::previous_dns`, `RecordGroup`, `explain_record`, `tool_host`, `zone_line`. One deliberate difference from the app: a delegation walk that fails leaves the other sources standing and sets DNSSEC to unknown, where the app fails the lookup. `Session::start_dns` has no destination to resolve; `Message::Origin` carries the source address toward the resolver. The report gains `records` (the reference answer) and `of_dns`. `rvrs dig` (`dig.rs`, alias `dns`) decides in `parse`: a name alone is the lookup (`one_question` false); `@server`, a type, a short flag or a `+option` is one question in dig's output, as is a pipe, `--classic` or the `dig` name. dig's output was diffed against dig 9.10.6 on macOS and differs in the first line only; keep it that way, including the tabs (`padded`) and the AD bit dig sets in its questions. One question is not a run and is not kept. In the Console DNS is `DnsTab` (Overview, Records, Compare, Trace on `1` to `4`, Tab for the next), `dns_row` and `dns_source`; `dns_key` takes the keys, `dns_lines` draws the open tab under tabs that stay put, and a record's details reuse the hop details column (`draw_record`, `record_actions`: the tools when `tool_host` names a host, Copy Value, Copy as Zone Line). The app has the same NXDOMAIN quirk the port kept: a name that doesn't exist reads "Resolved" in the headline because the SOA came back, while the verdict says "No address".

- **TCP traceroute** (`tcp.rs`, 2026-11-21, the first of the two tools ISP tickets asked for): `rvrs traceroute -T -p <port>`, Linux traceroute's own flags, default port 80. No root on either system. A probe is a TCP socket whose TTL is set before `connect`, so its SYN dies at that hop. macOS hands the router's ICMP message to an ICMP datagram socket of ours (`IcmpListener`, matched by the source port in the quoted TCP header, `quoted_tcp`), and the TCP socket itself only says `EHOSTUNREACH`, so a failed probe waits up to 60 ms for the message that names the router. Linux puts the message on the TCP socket's own error queue (`IP_RECVERR`), so no ICMP socket is opened there. The run starts with one connect at the system's TTL: a SYN-ACK is `open` (with the connect time and the MSS from `TCP_MAXSEG`), a reset is `closed`, nothing is `filtered` (`PortState`, sent as `Event::Port`, stored as `Run.tcp`, a `TcpProbe` with `#[serde(default)]` fields). An answering port is traced to the destination. A filtered one stops five silent hops past the last router that answered (`SILENT_HOPS`), and `Run::tcp_filter_note` names that router as where the SYN was last seen, worded as likely. At most six probes are on the wire (`WINDOW`), since each SYN that arrives costs the target a connection, and every socket closes with a reset (linger 0). It emits the traceroute's own events, so the pretty and classic looks, history and the report work unchanged. The report gains `probe` (`protocol`, `port`, `state`) and `connect` and `mss` in `measured`. Not there: the Console (it traces with ICMP), MTR and ping over TCP, UDP, and the iOS app (a gap on purpose, the user, 2026-11-21, marked in the parity table). Verified 2026-11-21 on macOS against open, closed and filtered ports and in the Debian container, where Docker's proxy answers at hop 2 for every target. A result is written beside its name, synced and renamed, so its file is whole or not there. A file that holds no result is removed at the start and counted as dropped, and `keeps` says `memory` while a result waits that has no file. `startedAgoMilliseconds` is added when a result is sent, from an `Instant` taken when the run started, and left out for a result from before a restart. `node/runner.rs` makes an admitted run with `Session`, handing the engine the address the guard resolved and checked, and ends it at `Admitted.deadline` or when told to stop. `node/service.rs` is the loop, one thread that owns everything and reads one channel: a heartbeat at start, every `heartbeatSeconds` and when `dropped` changes. The stream on a thread of its own (`events` from the heartbeat's answer when its scheme is the API's), given up after twice `keepAliveSeconds` of silence and opened again after a random wait in a window that doubles to 300 s and that `hello` sets back. A claim on `hello`, on `work`, every third of the lease while it holds anything, after a stream that failed, and at random between half of `claimSeconds` and all of it. A claim has a new 16-letter key, and one that got no answer is sent again as it was for two minutes, so the API gives the same attempts back. Verdicts: `keep` nothing, `stop` ends the run and sends it, `drop` ends it and sends nothing, and any other word stops the run and is named in the report's `error`. Results go out oldest first, one a turn of the loop, so a full outbox never keeps the node from a claim that is due. The first version sent them all in one go, 125 s for 500 results at 250 ms each, which is longer than the 90 s lease (the review of 2026-11-23). 200 and 201 are done when the answer's `id` is the run's (`is_receipt`), and any other 2xx is tried again. 409 is done, 429 waits `Retry-After`, any other refusal is given up and counted as dropped, and no answer is tried again. A 401 ends the runs and the loop (`Ended::NoToken`), after which `node.rs` idles and makes no call until the token file holds another token. 403 `FLEET_STOPPED` ends the runs, keeps the results and asks again in an hour. The report's `target` is set to the request's, since the API answers 422 for another, and a DNS or a BGP run would otherwise name what the tool made of it. Its `id` is the run's id and the attempt (`report_id`), which never repeats on a node and is the same every time the result is sent. The API refuses a report whose id the node used before, and `new_id` had six characters then (the same review). Its origin is `node` with the name, id and `metadataRevision` the heartbeat's answer gave. The thread that reads a stream ends by itself once nothing arrived for twice the keep-alive and five seconds (`timeout_per_read`, which ureq has since 3.5), so a connection that died without a word holds no thread and no socket. The first version left that thread until the stream's hourly cut (`LONGEST_STREAM`), which stays. SIGTERM and SIGINT stop the node (`catch_stops`), which a container needs since it is process 1. `crates/rvrs/src/remote.rs` is the asking side. Every tool's parser already took `--node`. `take_flags` in `main.rs` takes `--no-wait` and `--expires-in` out before a tool parses. `remote::traceroute`, `ping`, `mtr` and `dig` turn the parsed flags into the protocol's options, only what differs from the default, and refuse a flag with no option (`-s`, `-t`, `@server`). `remote::run` posts the request with a key, three tries, then reads `GET /v1/run-requests/{id}?wait=25` on a thread so Ctrl-C ends the waiting at once and leaves the run. It prints the state on stderr when that is a terminal, the result through `Run::from_report` and `trace::show`, an expired request as one sentence with the node's name and how long it waited, and a refused or failed run as its `error` with exit 1. `rvrs nodes` lists `GET /v1/nodes`. An MTR report's `HOST:` is the run's `from` when it has one. Tests: `node/service_tests.rs` runs the loop against a listener in the test that answers with the protocol's fixtures, with `Hands` standing in for the engines and the resolver so no packet is sent: a wake-up that never arrives, a page from a load balancer and a dropped connection before the API takes a result, a held run listed in every claim, `stop`, `drop`, an unknown verdict, a 401, a stopped fleet, a claim sent again with its key, a silent stream, a network that lets no stream through, a 200 that is a page and a 201 that names another run, an outbox of 300 results that goes out while the node still claims, and a stream's reader that ends when nothing arrives. A run ended at `secondsPerRun` by a real engine has no test, since it would send packets. - **Schedules** (2026-11-23, initiative C1 in `../ios-app/docs/initiatives/schedules-and-alerts.md`, released as rvrs 0.17.6 on 2026-11-23 with rvrs-dev/cli#11, built against the protocol's revision 2 while the API's half was built in `../app` (rvrs-dev/app#13, API 0.11). `docs/node.md` has the section for people). A schedule is a run a node repeats at an interval. The contract is the protocol page's section Schedules, with `GET /v1/nodes/me/schedules` for the node, `GET` and `POST /v1/schedules` and `GET`, `PATCH` and `DELETE /v1/schedules/{id}` for a person's install, the `schedules` event, `schedules` in the heartbeat's answer and `schedule` beside a result's report. `PROTOCOL` is 2. The rules live in `rvrs-core/src/node/schedules.rs`, pure, with the time handed in as an `Instant`: `Copy::read` reads an answer or the kept file (unknown fields ignored, an entry it can't read left out, 50 at most, each schedule once), `Schedules::replace` takes an answer (every next start is `startsInMilliseconds` from the answer, a start less than half an interval after the schedule's last one is left out there and only there, a refused schedule stays refused while the copy says the same about it, the copy's age starts over, and `Replaced::stop` names the schedules that left the copy while a run of theirs was going), `from_kept` starts each entry at a random time within its interval and gives the copy what is left of its `keepSeconds`, `due` hands back what to do now (`Due::Start` with the `Admitted` run already counted by the guard, `Due::Refuse` once per schedule, `Due::LeftOut` at a limit or while the last run is still going) and keeps each schedule's place in the interval, so a start the node missed is passed over and never made up. `hold` is the stopped fleet, `clear` is no token or an API without schedules, `expired` is a copy older than `keepSeconds`. A restart never makes a kept copy fresh (the review of 2026-11-23: the first version gave a kept copy its whole `keepSeconds` again at every start, so a node that restarted now and then without its uplink ran a deleted schedule for good). `Age` is `readAt`, the node's clock at the answer, and `usedSeconds`, how long the node has run with the copy. `Age::at_start` is the larger of `usedSeconds` plus the ten minutes a crash could have left unwritten (`AGE_WRITTEN_EVERY_SECONDS`) and the clock's time since `readAt`, which counts nothing when the clock reads earlier than `readAt`, since such a clock is not synchronized. A copy with nothing left is held as expired from the start. A schedule that leaves the copy stops its going run (the same review, the user's decision: pause, delete or no longer matching means stop now). The loop sets that run's stop flag (`stop_scheduled`), and the run's result goes out with the outcome `stopped` and the schedule's id. A schedule that stays in the copy with another interval or other options keeps its run, and a copy that ran out stops none. `node/service.rs` is the wiring: `read_now` is set by `hello`, by a `schedules` event, by a heartbeat's answer that names another version, when a pause ends and once when the copy expired. The loop makes the read itself, so there is one at a time. A read that got no answer is made again in a window that doubles to 300 s, the API's own 404 clears the copy until the next `hello`, 429 waits, and any other refusal is not repeated. `start_due` runs at the top of every turn of the loop and after each call to the API, because a call that gets no answer blocks the loop for its whole wait, 20 s for most and 30 s for a result. A scheduled run goes through `Guard::admit`, `Guard::destination` and the same runner as a claimed run (`make`), its report's id is 26 random characters (`scheduled_report_id`), and its result is the outbox body `{ report, schedule }`, which keeps the schedule's id across a restart. A name that resolves to an address the node sends nothing to refuses the schedule too. `node/kept.rs` keeps the copy as `schedules.json` in the state folder, never inside `outbox/`, where a file without a report is removed as unreadable. It leaves `startsInMilliseconds` out and holds the copy's age beside the copy, as `readAt` and `usedSeconds`. `load` answers no copy for a file without the age, which is what a build before 0.17 would have written. The age is written with the copy, at a start from the kept copy (so a node that restarts every few minutes still uses its copy up), every ten minutes while the node holds schedules, and at a clean stop (`keep_age`). A copy without schedules is written once and its age never, so a node without schedules leaves the disk alone. A file that is gone is written again, whatever the process wrote before, and a copy that can't be written is said once in the log. 401 deletes the file. Every run the node makes carries the metadata revision the node held when the run started (`Made.revision`, the same review: `report_of` wrote the revision at the run's end, so a tag edited during a long MTR relabeled it), and a refusal the one at its check. The log has one line per scheduled run and per run left out, and names a schedule by its id. `crates/rvrs/src/schedule.rs` is the person's side: `rvrs schedules`, `rvrs schedule add <tool> <target> --every <interval>` with exactly one of `--node` (repeatable), `--fleet <selector>` and `--all-nodes`, plus `--name` and `--json`, and `show`, `pause`, `resume` and `rm` (also `remove`) with an id or the start of one. `take_add_flags` takes the schedule's flags out and the tool's own parser reads the rest, so the options are the ones `--node` sends (`remote::traceroute` and the others) and the same flags are refused. `--no-wait`, `--expires-in`, `--classic` and `--case` are refused. `account::request` sends `PATCH` since this. Tests: the module's own, `node/service_tests.rs` with the copy's numbers scaled to one second (a copy read after `hello`, a `schedules` event, a schedule that leaves the copy, the API out of reach and back, a refused schedule, the API's 404, a kept copy with the API away, 401, a stopped fleet, a run still going), `node_protocol.rs` for the examples, and `schedule.rs` against `schedule.request.json` and `schedule.selector.request.json`. Decisions taken in this build and not confirmed by the user: the half-interval rule is applied when an answer arrives and never to a start that is late by the node's own doing. A node that got another 403 than `FLEET_STOPPED` starts no scheduled run for the hour it waits. An API's own 404 on the read deletes the kept copy. The second schedule of the protocol's examples names 192.0.2.53, a documentation address, which a real node refuses as reserved. Not built: reading a schedule's runs in the CLI (`GET /v1/runs?schedule=`), changing a schedule's options, interval or nodes (`PATCH` takes them, the CLI only pauses and resumes), `rvrs alerts`, a check of the selector before it is sent, and anything in the Console. The agent skill has a section on schedules since 0.17.0 (`references/nodes.md`, A schedule, and eval scenario 19): an agent makes one only when the person asks for a run that repeats.

- **Run ids** (2026-11-23, the last finding of that review). `new_id` (`rvrs-core/src/model.rs`) makes 26 characters from the 31-letter alphabet, 128 bits from `/dev/urandom`, with the standard library's hash keys as the fallback where there is no random device. Until then an id had six characters, about 30 bits. The account tells an install's runs apart by this id for good (the unique index on install and `client_id`), so on a busy install the second run with an id got the first one's answer from `POST /v1/runs` and never reached the account. The chance of one such repeat on an install was 5.5% after 10,000 runs. People still type six characters: `History::find` always took the start of an id, `rvrs history`, `rvrs saved` and `rvrs case <name>` show the first six (`short_id`), or as many as tell every run in history and saved apart (`id_width`, `known_id_width` in `commands.rs`), messages name a run by six, and completion offers what the lists show. `--json` has the whole id. An id from before keeps its six characters and is found as before. A case's id comes from `new_id` too and nobody types it. `local_id` in `sync.rs`, the id a run from another product gets on this device, still has six characters worked out from its id in the account. It is never sent anywhere, and `receive` skips a run whose `local_id` is taken.
- **Tags and location** (2026-11-23, initiative B4 in `../ios-app/docs/initiatives/tags-comments-location.md`, the user's decision that day: tags everywhere, never labels). A tag is a key and a value on an install (`isp=telia`), a location is `lat`, `lon`, an optional `place` and a `precision`. A node declares both in its configuration, the web app edits on top of the declaration, the API works out the tags that count, and the CLI only declares. What exists here is the contract and the parsing. `schema/node-config.md` is the node's configuration: flags `--tag key=value` (repeatable), `--location <lat>,<lon>`, `--place`, `--location-precision <exact|area|city>`, the `RVRS_NODE_TAGS`, `RVRS_NODE_LOCATION`, `RVRS_NODE_PLACE` and `RVRS_NODE_LOCATION_PRECISION` environment, and a `node.json` in the config folder (JSON, as every file the CLI keeps there, in the shape the heartbeat carries), where a flag beats the environment and the environment beats the file, key by key for tags and whole for a location. `rvrs-core::node_config` parses and checks all of it (`NodeDeclaration::from_sources` with the environment handed in as a reader, `from_file`, `parse_tag`, `parse_location`, `round_location`), and every refusal is a whole sentence that names the input. `rvrs node` (`node.rs`) reads its own flags and `RVRS_NODE_*` before it refuses, so a bad tag or coordinate exits 2 with its sentence and a good declaration reaches today's refusal. The enroll and heartbeat bodies in `schema/node-protocol` gained optional `tags` and `location` (omitted is unchanged, `{}` is no tags, the whole declaration every time, the enroll sets it only when it makes the node, a web edit is never undone), and the run report gained `origin.tags` and `origin.location`, which the API writes from the install's values and replaces whatever the sender wrote (`tagged.json` is the fixture, `ReportOrigin` reads a shape it doesn't know as absent). A run is tagged as it was when it ran (review of 2026-11-23): every change to an install's tags or location makes a revision, the enroll and heartbeat answers carry the current one as `node.metadataRevision`, and a node writes the one it last read into `origin.metadataRevision` and keeps it with the run in its outbox. The API checks it against that node's own history and writes the tags and location itself. The node loop that does this is B5. The precision is a bounded string and never a closed list, and the API rounds the coordinates (4, 2 and 1 decimals) before it stores them. Not built: the node, the routes, the heartbeat's handling, the packages that write the configuration (B5 and B6), `--tag` selectors in `rvrs history`, and a way for a node to take a declared location back (the protocol has none, so a person clears it on the web).
- **Sockets.** `SOCK_DGRAM` ICMP, no root. macOS delivers every ICMP message about our probes on the socket, IPv4 with its IP header. Linux delivers echo replies on the socket and other routers' errors on the error queue (`IP_RECVERR`, `recvmsg(MSG_ERRQUEUE)`), and rewrites the echo identifier, so replies are matched by sequence alone there (`IcmpSocket::rewrites_identifier`). Where Linux refuses the datagram socket (`EACCES`, `EPERM`, `EPROTONOSUPPORT`), `IcmpSocket::open` tries `SOCK_RAW` and keeps the datagram error if that fails too: a raw socket gets every ICMP message with its IPv4 header, errors as ordinary packets, our identifier intact, so the parser and the identifier check filter. Unikraft has no unprivileged ICMP, and the site's image runs the CLI that way; verified 2026-11-17 on Unikraft Cloud `was` (vercel.com reached in 13 hops, also started from Node). Verified 2026-11-15 in a Debian 13 container (aarch64, Docker Desktop), as root and as a normal user: hop 1 arrives through the error queue, the destination as an echo reply, and the lines match the system's `traceroute -I`. Docker Desktop's network hides every router after its own gateway, for the system traceroute too, so a long path on Linux has not been seen yet; check one on a real Linux host. The refusal message for a closed `ping_group_range` is untested as well.
- **Model.** `Run::apply(event)` folds events into hops and returns an address the first time a host answers, which is when `Session` starts its lookups. A `Slot` is `Pending`, `Lost` or `Reply`. `Run::path()` is the hops up to the farthest one that answered; a silent target keeps its silent hops in `hops` so the classic look can print them. `groups(run)` is the app's `TraceGrouping`, ported rule for rule.
- **Rate limits.** Rounds are back to back, so a Linux router with the default `icmp_ratelimit` answers one probe per hop and drops the rest (seen on Docker's gateway). That is the router's doing and `-z` spaces probes out; if it shows up on real paths, pace the rounds before touching the wait.
- **BGP.** Ported from the app's `Networking/BGP`, `Models/BGPResult.swift` and the BGP screens, sentence for sentence (the user's ask, 2026-11-20: "the full bgp functionality in the cli like in ios"). `bgp::result` is the stored result with the verdict, summary, headline, the changes read off the origin timelines, the traceroute comparison and the text export. `bgp::ripestat` is the client and the typed data calls. `bgp::lookup::run` is the engine: scoped threads, one per part, each sending a `BgpEvent` as its call answers (`prefix-overview` then `rpki-validation` per origin AS, `routing-status`, `looking-glass` folded into distinct paths, `routing-history`, `bgp-update-activity`, then the origin network: `as-overview`, `rir`, `rir-stats-country`, `asn-neighbours`, `ris-prefixes` and origin validation for 40 prefixes, six at a time). `Run::apply_bgp` folds the events; a lookup that finds neither a route nor a network ends exhausted, so the exit code tells "no route observed" from a result. `Session::start_bgp` forwards the events and ends the run at once on a stop, since a data call can take 20 seconds to give up. `bgp::glass` holds the four looking glass adapters (Alice-LG, lg.cgi, hyperglass 1 and 2, bird-lg-go) behind `describe`, `routes`, `sessions` and `test`, with `router_text` reading Junos, Cisco/FRR and BIRD output; it uses no regex crate, `scan.rs` holds the hand scanners. `bgp::Glasses` is the store (`looking-glasses.json` in the config directory, snake_case fields, not the app's JSON). - **Leaving a live run.** `App::retire` stops a run that is still going when another is started or the Console quits, and keeps what it measured in history, so a long MTR is never thrown away.
- **Quitting.** Only a list quits (esc with no search, nothing typed and no row selected, or Ctrl-C anywhere). A run and a hop's details have no `q` (the user's call, 2026-11-15): left steps back out. `q` closes the help, which is no view.
- **Keys first, search and help** (2026-11-25, feedback from a k9s user the user passed on: "lets NOT autofocus the box", a direct key per tool with tab kept beside it, `/` on every list, and help that summarizes each tool's commands). Every key is a command until the field has the keys (`App::field`), as in k9s. `t m p d b` on a list (the run picker's letters, `run_picker::letter`, through `tool_of`) pick the tool and give the field the keys, `:` does it for the tool chosen last, from a list, a result or Account, and Return on an empty list does it too. In the field typing is the target, the arrows pick among the hosts it suggests, tab and shift-tab pick the tool, and esc empties it and gives the keys back. In a result the same letters keep acting on the selected hop or record. `/` opens a search line at the foot (`App::search`, `searching`, `search_key`): typing narrows the list on screen and the selection lands on the first hit (`land_search`), Return keeps the search and gives the keys back, an arrow moves through the hits, esc drops it. The panel title shows it after the count as k9s writes it (`Recent(all)[3] </git>`, `panel_searched`). It narrows Recent, Favorites and Cases (`filter`, the search alone), a trace's or an MTR's hops by every address that answered, its name and its network (`hop_found`, `hop_rows`, `step_hop`; a filtered row names its network, since the hop that names it may be hidden), a DNS lookup's records in Overview and Records (`record_found`, `dns_records`, `grouped_records`), and a BGP lookup's selectable rows (`Screen::item` skips a row the words aren't in; the keys read the rows at the width they were drawn, `bgp_columns`). A search belongs to one list: `key` compares `place` before and after a key and drops it when the screen shows another. `d` shows the selected hop's, record's, AS path's or RPKI result's details and hides them, as k9s describes; so the MTR's rounds strip moved from `d` to `v`, and BGP History's range from `d` to `o`, beside the other `o` cycles. `?` opens `console_help.rs`: pages Keys and one per tool, opening on the tool in view (the Console's keys on a list). A tool's page has the keys its result takes, then `help::<tool>` as `--help` prints it, so the commands are never written twice. tab turns the page, a tool's letter opens its page, `?` the Keys page (and closes it from there), the arrows scroll.
- **Console.** `console::App` holds the field, the selected tool (tab switches between the available ones), the list (Recent, Favorites or Cases, narrowed by the search), the open case and the case picker, the shown run (live or saved) and the hop sheet. `console_run.rs` is the run picker (the user's ask, 2026-11-20): `r` on a run in a list or on the host a result's selection names (a hop, a record's host, a BGP network, prefix or address) opens every tool that can take that host (`tools_for`: an AS number or a prefix only BGP, an address no dig, a private address no BGP), and `R` runs the open run again. The tool chosen last is kept in `console.json` in the config directory, written by `open` whenever it changes, and `Tool::ALL` lists iperf3 last. An MTR charts latency, jitter (the move from one reply to the next) and loss (over a 10-round window) above the table, side by side from 120 columns, and in a hop's details (`mtr_charts`, `metric_chart`). `draw` is one panel: Recent (or suggestions) at the start, the run once one is open. Tests render to ratatui's `TestBackend` and assert on the text.

## Conventions

- Versions come from git (`crates/rvrs/build.rs`, the user's call, 2026-11-16, so a server always shows what it runs): `RVRS_VERSION` is `VERSION` (major.minor) plus the commits since `VERSION` last changed, one more for a dirty tree; `RVRS_COMMIT` is the short commit, `-dirty` when uncommitted. `help::VERSION` and `help::COMMIT` read them, and `rvrs --version` prints `rvrs 0.2.3 (4ea5d4e)`. Never set a version in `Cargo.toml` to change what people see; bump `VERSION` and commit it with a bigger change. Without git the crate's own version and "unknown" stand in.
- Stored types (`Run`, `Hop`, `Slot`, `Network`) are read back from `history.json` across versions. A new field carries `#[serde(default)]` and a test that an older file still loads, or the person's history is gone.
- The report is the iOS app's `RunReport`, field for field (`../ios-app/rvrs/Models/RunReport.swift`), with `id`, `origin` and DNS `sources` since 2026-11-20, in both. Change both together. Its schema is written down in this repo, as JSON Schema with fixtures, before the API stores runs, and the API and the app mirror it (see Repositories).
- Statistics and sentences match the app: jitter is the mean step between consecutive replies, percentiles are nearest rank, summaries and interpretation are the app's strings. Port, don't reinvent.
- rvrs's own flags are long only, so they never collide with a tool's short flags.
- An unsupported flag is an error that names it. Never ignore a flag when ignoring it changes the result.
- Data goes to stdout. Errors go to stderr as `rvrs: <one sentence>`. Exit 0 for a run that was made, 1 for one that couldn't be, 2 for usage. ping keeps its own codes: 0 answered, 1 no reply, 2 couldn't run.
- Color is the terminal's sixteen colors plus bold and dim, so it follows the person's theme. The one exception is the logo at the Console's top right (`LOGO`, `LOGO_MASK`, `logo_lines`): the try shell's art in its own colors (the user's design, 2026-11-20), whole where the header has room, cut to the mark and the rules (`LOGO_CUT`) where it doesn't, hidden on a narrow terminal. Never state something by color alone. `COLOR.md` gives each figure and each state one color on every surface, and the CLI follows it since 2026-11-25. A figure on a chart takes its own color: latency in its tones, jitter magenta, loss red. A state takes its own: green for a reached destination or a stable verdict, yellow for something worth a look such as no reply from the target or occasional loss, red for a failure, an Invalid route and loss that reaches the destination (a ping packet with no reply, the LOSS tile, the Packet loss verdict), blue for a run in progress, and dim for none, such as a paused schedule. Loss in a hop table is red where it reaches the destination (`Run::loss_carries`), and at a middle hop whose later hops are clean it is yellow in the Console's traceroute and gray in an MTR. A count is ink, so the BGP sparks of peers and updates have no hue. The spinner is chrome in blue.
- No call to a system network tool, ever. `pbcopy`, `wl-copy`, `xclip` and `open` are used for the clipboard and the browser only.
- Every string follows `.claude/skills/rvrs-voice/SKILL.md`, and every term `GLOSSARY.md`. Both are copies of the app's; edit there and copy.
- A networking change comes with a parsing or model test. A live trace against a public host is the integration check.
- A new build feature is a feature of `crates/rvrs` in `default`, a row in `features::ALL`, a name in `install.sh`'s `features` line and in the node protocol's `features`, and a refusal where its command starts. Its dependencies are optional and come in with the feature. A crate that comes into the small build goes into `scripts/small-build.deps` in the same commit, with its size in the message.
