# rvrs CLI

The `rvrs` binary for macOS and Linux (Rust 2021, no async runtime): the network tools engineers already type, with their flags, plus what the rvrs app does. traceroute, ping, MTR, dig and BGP are the tools today; iperf3 is next. The same binary later runs as a node (`rvrs node`). Sibling repos: `../ios-app` (the iOS app, whose Swift engine and models this ports; its `WORLDVIEW.md` says where rvrs is going and `docs/tasks/cli-bootstrap.md` is this repo's plan), `../app` (the API; runs, accounts and nodes land there).

## What the user wants

- State-of-the-art ease of use, in the spirit of gh, minikube and k9s. Nothing to set up, good help, color, completion, plain errors that name the next step.
- A 1:1 drop-in for the original tools: same flags, and the original's output wherever a script could be reading.
- `rvrs` alone opens the Console, a small TUI with the app's interactions. A tool command (`rvrs traceroute`, later `rvrs ping`) prints a styled result and returns. It never opens a TUI.
- Hops grouped by network, as in the app.
- Parity with the app in features, patterns and words: read `../ios-app/PARITY.md` (it lives only in the private app and API repos) before adding or changing anything a person sees, and update its table in the same change.
- Sharing only for signed-in people: a run is saved to the account and the command links to its run page. Nothing is uploaded otherwise.
- Keep README.md, `docs/` and this file current with every change. The README is short on purpose (the user's call, 2026-11-20: "really EASY to digest"): what rvrs is, the tools, install, using it in place of the originals, privacy and links. Flags, keys, the report, files and every request rvrs makes live in `docs/` (one file per tool, `console.md`, `commands.md`, `privacy.md`). No sentence in the README explains how the installer or the binary works inside.
- **Releases** (2026-11-20, the user's go): `.github/workflows/release.yml` runs on a tag `v<VERSION>.<patch>` that matches the commit's computed version, or from Actions > Release > Run workflow, which tags the newest `main`. It builds `aarch64`/`x86_64-apple-darwin` on macos-14 and `x86_64`/`aarch64-unknown-linux-musl` on Ubuntu runners (musl-gcc), packs `rvrs-<target>.tar.gz`, builds a `.deb` (cargo-deb) and an `.rpm` (cargo-generate-rpm) per Linux architecture, writes `SHA256SUMS`, and publishes them with `install.sh` as a GitHub release. The `homebrew` job writes `Formula/rvrs.rb` into `rvrs-dev/homebrew-tap` with `scripts/formula.sh`; it needs the secret `TAP_TOKEN` (a token that can push to the tap) and skips with a line when it's missing. `.github/workflows/ci.yml` runs fmt, clippy and the tests on macOS and Linux for every push and pull request. `rvrs update` and `install.sh` both check the archive against `SHA256SUMS`. A binary in `/usr/bin` is a package (`Install::Package`) and `rvrs update` leaves it to the package manager.
- `install.sh` is the installer the site serves as `rvrs.dev/install.sh` (README, Install), a redirect to the newest release's `install.sh`. On a terminal it asks per tool whether rvrs should run as traceroute, ping, mtr and dig (default no, reading answers from `/dev/tty` so it works under `curl | sh`) and whether to set up completion for the shell in `$SHELL` (default yes); `--link`, `--no-link` and `--yes` answer for it, and without a terminal it asks nothing, links nothing and sets up nothing. It downloads `rvrs-<arch>-<os>.tar.gz` from the latest GitHub release (`x86_64`/`aarch64`, `apple-darwin`/`unknown-linux-musl`, the archive holding `rvrs` at its top level), installs to `~/.local/bin` (`RVRS_INSTALL_DIR`), and links `traceroute`, `ping`, `mtr` and `dig` next to it when asked, never over a real file, then says when the links are shadowed on `PATH`. `RVRS_INSTALL_ARCHIVE=<file>` installs a local archive, which is how it is tested.

## Commands

```bash
cargo build --release          # target/release/rvrs
docker run --rm -v "$PWD":/src:ro -v rvrs-target:/target -e CARGO_TARGET_DIR=/target rust:1-slim sh -c 'cp -r /src /b && cd /b && cargo test && cargo build --release && /target/release/rvrs traceroute -n 1.1.1.1'   # the Linux check
cargo test                     # unit tests; none touch the network
cargo clippy --all-targets     # keep at zero warnings but the as_chunks note
cargo fmt
RVRS_HOME=/tmp/x target/release/rvrs traceroute 1.1.1.1   # a live check that leaves your history alone
```

With Homebrew's rustup, `/opt/homebrew/opt/rustup/bin` must be on PATH. To see the grouped output or the Console without a real terminal, run it inside tmux and read the pane: `tmux new-session -d -s t -x 130 -y 36 "zsh -f"`, `tmux send-keys -t t "target/release/rvrs 1.1.1.1" Enter`, `tmux capture-pane -t t -p`.

## How it works

- **Engine.** `engine::run` sends one probe to every hop per round, rounds back to back, 5 ms apart, on one thread that also reads replies. Probes are matched by echo sequence (a counter mapped to TTL and round, so up to 255 hops and 10 probes per hop). A reply from the destination stops probing beyond it. A probe's wait is `-w` until the destination has answered, then ten times the slowest reply, at least 500 ms. Events: `Sent`, `Reply`, `Lost`, `Finished`, `Failed`.
- **Ping.** `engine::ping` sends one echo request per interval at one TTL, matches replies by sequence, and calls a packet lost after `-W` (2 s by default). A router that answers instead of the target is a `PingRefused` and a `Slot::Refused`: sent, not received, and printed as ping prints it. A ping run keeps every packet in one hop (`Run::packets()`), as the app does. `Verdict::of(stats)` is the app's `ConnectionInsight`, thresholds and words. On a terminal each settled packet is printed once above a live region (`LiveRegion::print_above`) that holds the sparkline and the status line; the closing block is the figures and the verdict. The reply's TTL comes from the IPv4 header on macOS and from a control message (`IP_RECVTTL`, `IPV6_RECVHOPLIMIT`) elsewhere.
- **MTR.** `engine::mtr` is the traceroute engine paced: one probe to every hop per round, a round per interval (1 s; routers rate-limit their replies at anything much faster), until `-c` rounds or a stop. Rounds have no upper bound, so MTR has its own events (`MtrSent`, `MtrReply`, `MtrLost`, round as `u32`) and a hop grows a slot per round (`Run::mtr_slot`). A run keeps its newest `Run::MAX_ROUNDS` (1200) rounds: older ones are dropped from the front of every hop and `Run::first_round` counts them, as the app caps its samples. The first round probes up to `-m` to find the path at once; while the destination is unknown, later rounds stop `-U` (5) hops past the farthest hop that answered. The app's rules are ported word for word: `Run::chart_hop` (the destination, else the farthest hop that answered), `loss_carries` (loss at a middle hop counts only when the chart hop loses too), `rate_limited_hops` (two losses and 10%), `rate_limit_note` (the app's sentence, listed as `ListFormatter` lists), and the report adds the verdict on the destination and the note to `interpretation`. Loss is red only when it carries and gray otherwise, in both looks. `mtr::report_lines` is mtr's `-r` report, column for column (a loss of 100.0% takes a space from the host column, as mtr's does); a pipe, `-r`, `--classic` or an `mtr` symlink gets it, with 10 rounds when `-c` doesn't say. On a terminal `mtr::table` is redrawn in place: hops under their network, Loss, Snt, Last, Avg, Best, Worst, Jitter, and from about 150 columns a sparkline of each hop's newest rounds (`mtr::sparkline`, scaled to the slowest reply of the run). `-j` is the rvrs report, not mtr's JSON. In the Console an MTR runs until `s` (`App::mtr_lines`): the same figures with a ROUNDS strip, `d` for a wide strip of each hop's rounds (`mtr_history`; not "history", which the glossary keeps for stored runs), the chart hop's latency by round under the table, the selected hop's own chart in the details column, and Run MTR (`m`) among a hop's actions. Verified 2026-11-20 on macOS and in the Debian container, as root and as a normal user.
- **DNS.** Ported from the app's `Networking/DNS` and `Models/DNSResult.swift`, sentence for sentence (the user's ask, 2026-11-20: "feature parity with DIG and how we do DNS on the iphone"). `dns::message` builds and parses RFC 1035 messages with EDNS(0); a `Presentation` picks the app's short values or dig's zone-file values. `dns::client::query` asks over UDP and again over TCP when the answer is truncated. `dns::lookup::run` asks the device's resolver (the first `nameserver` in `/etc/resolv.conf`, labeled Router when private), Cloudflare, Google, Quad9 and any `--resolver` for nine types each on scoped threads, and walks the delegation from the root for the authoritative answer, DS at each parent, DNSKEY and RRSIG. It reports through `DnsEvent`, which `Run::apply_dns` folds into `Run.dns` (a `DnsResult`, stored with the run; older history files load without it). DNSSEC is presence only: say "signed", never "verified". `dns::result` holds the rules the screens share: `Diff` (notes with their usual reason, `status` per source), `verdict`, `headline`, `summary`, `changes` against `History::previous_dns`, `RecordGroup`, `explain_record`, `tool_host`, `zone_line`. One deliberate difference from the app: a delegation walk that fails leaves the other sources standing and sets DNSSEC to unknown, where the app fails the lookup. `Session::start_dns` has no destination to resolve; `Message::Origin` carries the source address toward the resolver. The report gains `records` (the reference answer) and `of_dns`. `rvrs dig` (`dig.rs`, alias `dns`) decides in `parse`: a name alone is the lookup (`one_question` false); `@server`, a type, a short flag or a `+option` is one question in dig's output, as is a pipe, `--classic` or the `dig` name. dig's output was diffed against dig 9.10.6 on macOS and differs in the first line only; keep it that way, including the tabs (`padded`) and the AD bit dig sets in its questions. One question is not a run and is not kept. In the Console DNS is `DnsTab` (Overview, Records, Compare, Trace on `1` to `4`, Tab for the next), `dns_row` and `dns_source`; `dns_key` takes the keys, `dns_lines` draws the open tab under tabs that stay put, and a record's details reuse the hop details column (`draw_record`, `record_actions`: the tools when `tool_host` names a host, Copy Value, Copy as Zone Line). The app has the same NXDOMAIN quirk the port kept: a name that doesn't exist reads "Resolved" in the headline because the SOA came back, while the verdict says "No address".
- **Update.** `rvrs update` (`update.rs`, the user's ask, 2026-11-20: "a super smooth ux mechanic to update the cli") looks at where the running binary lives (`install_of`): inside a checkout's `target` it fetches, lists the new commit subjects, fast-forwards and runs `cargo build`, and leaves a checkout with uncommitted changes or its own commits alone; under Homebrew it names `brew upgrade rvrs`; anywhere else it downloads `rvrs-<target>.tar.gz` from the latest GitHub release, as `install.sh` does, checks that the new binary runs, writes it beside the old one and renames it over it, so links to `rvrs` keep working. `RVRS_UPDATE_ARCHIVE=<file>` stands in for the download, which is how the binary path is tested (the checkout path was run end to end in a scratch clone). No release exists yet, so against GitHub the binary path can only say so. Between updates `look_when_due` starts `rvrs __update-check` as a detached process at most once a day, after a tool's result on a terminal and when the Console opens; it writes `update.json` in the cache folder, and `notice` turns that into one line after a result, in `rvrs status` and in the Console's header. The look is the only request rvrs makes that the person didn't ask for, so it is named under What leaves this device in the README and `RVRS_UPDATE_CHECK=0` turns it off. git, cargo and tar are called for this; they are not network tools in the sense of the rule below.
- **Sockets.** `SOCK_DGRAM` ICMP, no root. macOS delivers every ICMP message about our probes on the socket, IPv4 with its IP header. Linux delivers echo replies on the socket and other routers' errors on the error queue (`IP_RECVERR`, `recvmsg(MSG_ERRQUEUE)`), and rewrites the echo identifier, so replies are matched by sequence alone there (`IcmpSocket::rewrites_identifier`). Where Linux refuses the datagram socket (`EACCES`, `EPERM`, `EPROTONOSUPPORT`), `IcmpSocket::open` tries `SOCK_RAW` and keeps the datagram error if that fails too: a raw socket gets every ICMP message with its IPv4 header, errors as ordinary packets, our identifier intact, so the parser and the identifier check filter. Unikraft has no unprivileged ICMP, and the site's image runs the CLI that way; verified 2026-11-17 on Unikraft Cloud `was` (vercel.com reached in 13 hops, also started from Node). Verified 2026-11-15 in a Debian 13 container (aarch64, Docker Desktop), as root and as a normal user: hop 1 arrives through the error queue, the destination as an echo reply, and the lines match the system's `traceroute -I`. Docker Desktop's network hides every router after its own gateway, for the system traceroute too, so a long path on Linux has not been seen yet; check one on a real Linux host. The refusal message for a closed `ping_group_range` is untested as well.
- **Model.** `Run::apply(event)` folds events into hops and returns an address the first time a host answers, which is when `Session` starts its lookups. A `Slot` is `Pending`, `Lost` or `Reply`. `Run::path()` is the hops up to the farthest one that answered; a silent target keeps its silent hops in `hops` so the classic look can print them. `groups(run)` is the app's `TraceGrouping`, ported rule for rule.
- **Rate limits.** Rounds are back to back, so a Linux router with the default `icmp_ratelimit` answers one probe per hop and drops the rest (seen on Docker's gateway). That is the router's doing and `-z` spaces probes out; if it shows up on real paths, pace the rounds before touching the wait.
- **BGP.** Ported from the app's `Networking/BGP`, `Models/BGPResult.swift` and the BGP screens, sentence for sentence (the user's ask, 2026-11-20: "the full bgp functionality in the cli like in ios"). `bgp::result` is the stored result with the verdict, summary, headline, the changes read off the origin timelines, the traceroute comparison and the text export. `bgp::ripestat` is the client and the typed data calls. `bgp::lookup::run` is the engine: scoped threads, one per part, each sending a `BgpEvent` as its call answers (`prefix-overview` then `rpki-validation` per origin AS, `routing-status`, `looking-glass` folded into distinct paths, `routing-history`, `bgp-update-activity`, then the origin network: `as-overview`, `rir`, `rir-stats-country`, `asn-neighbours`, `ris-prefixes` and origin validation for 40 prefixes, six at a time). `Run::apply_bgp` folds the events; a lookup that finds neither a route nor a network ends exhausted, so the exit code tells "no route observed" from a result. `Session::start_bgp` forwards the events and ends the run at once on a stop, since a data call can take 20 seconds to give up. `bgp::glass` holds the four looking glass adapters (Alice-LG, lg.cgi, hyperglass 1 and 2, bird-lg-go) behind `describe`, `routes`, `sessions` and `test`, with `router_text` reading Junos, Cisco/FRR and BIRD output; it uses no regex crate, `scan.rs` holds the hand scanners. `bgp::Glasses` is the store (`looking-glasses.json` in the config directory, snake_case fields, not the app's JSON). There is no original tool to match, so a pipe gets the app's Copy Results text and `--json` the report. Where the CLI differs from the app on purpose: `glass add` tries each type where the app asks for one, which is worth taking back to the app. The six defects found while porting (an uncovered address stuck on "Looking up", a "New origin AS observed" at the start of the 90-day window, "1 prefixes" and "1 networks", the report's sentence cut inside a holder's "Inc.", a doubled full stop after a holder in a change line, the last IPv6 prefix dropped after a leading prefix) are fixed in the app too (2026-11-20), so both read the same.
- **Session.** Resolves on a thread, runs the engine on it, forwards events, and looks hosts up as they first answer: reverse DNS on a thread each through getnameinfo, networks through four workers that share a queue and keep their connection to RIPEstat open. A network is shown as soon as its announcement is known and gains its location in a second step (`Message::Located`), because RIPEstat takes anywhere from 80 ms to over a second for an address it hasn't cached. Only complete answers go to the one-week disk cache. `pump(timeout)` folds what is ready into the run. A result never waits on lookups: the command gives them 1.5 s after the last probe (2.5 s on a terminal, where the result is already on screen), the Console saves after 3 s.
- **Looks.** `trace::look` decides: `--json` is the report; a pipe, `--classic` or a `traceroute` symlink is the classic look; a terminal gets `pretty`, redrawn in place by `term::LiveRegion` and clipped to the terminal's height while live. `pretty` paints through `Style`, and the Console turns the same painted lines into ratatui spans (`ansi_line`), so the grouped table exists once.
- **Console look.** Modeled on k9s at the user's request (2026-11-15: "WAY more fancy", still easy): a six-row header (facts in yellow labels, the tools only while the Target field has the keys, the keys that work now as `<key> Label` in columns of four, the `// rvrs` logo), the Target prompt (`traceroute> `), one framed panel titled `Name(scope)[count]` (`panel`), a selected row in black on cyan, and the section tabs on the last line, followed by where you are inside the section (the tool, the hop). Charts are `column_chart` (eighths of a row, a red mark for a missing value). Latency is green under 50 ms, yellow to 150 ms, red beyond (`style::latency_tone`), in the Console and in command output; never a color without its number. Columns drop as the terminal narrows and the header goes under 22 rows.
- **Saved runs, cases and origin.** `History::saved()` is the same store type on `saved.json` without the 500 limit: whole runs, apart from history. `History::saved_in` renames the file earlier versions kept these runs in when `saved.json` is missing, so nobody loses a run; that one constant (`EARLIER_SAVED` in `history.rs`) and its test are the only places the old word is left. `cases::Cases` (`cases.json`: `{"cases": [{"id", "name", "run_ids", "created_at"}], "last_used": id}`) holds the cases: names compare trimmed and without case, blank is refused, a run sits in several cases or none, deleting a case keeps its runs saved, and loading drops run ids that are no longer saved. `cases::save` is the one way to save, for the commands and the Console alike: without a case name the run also goes into the case used last (if it still exists; a run saved before stays where it is), with a name it goes into that case, made when new, which becomes the case used last; `cases::unsave` removes a saved run and its place in every case. Commands: `rvrs save [id] [--case <name>]`, `rvrs saved`, `rvrs saved remove <id>`, `rvrs case` (alias `cases`), `rvrs case <name>`, `rvrs case new|rename|delete|add|remove`, `--case <name>` on `rvrs traceroute` and `rvrs ping` (saved after the run is printed, the confirmation on stderr), and the hidden `rvrs __cases` for completion. In the Console `s` saves a finished run, open or selected in the list, or removes it from saved runs (a star marks saved rows); on a running run `s` is Stop, which is why saving could keep the letter. `a` opens the case picker (`Picker`, drawn over the middle like the help: every case with a check where it holds the run, space toggles, typing goes to the New case row and Return makes the case). ⇧3 Cases lists the saved runs flat while there is no case; with cases its first level is All saved plus each case with its count, newest run and "used last" (`Rows::Cases`), → goes into one (`App::case`, a `Scope`), ← or esc comes back with that case selected, and `x` inside a case takes a run out of that case only. The sections are tabs in the footer, `Section::ALL`: Console (the Target field and Recent), Favorites, Cases, reached with shift and their number from anywhere, also while typing (`Section::of` reads the shifted digit of US, UK, German and Danish layouts). The user replaced capital letters with this on 2026-11-15, after R, B and F didn't work for them; a new part of rvrs, such as login, becomes a section with the next number. Right goes into the selected entry and left comes back out, everywhere; letters are shortcuts only while a row is selected, because otherwise they type into the Target field. The user set these keys on 2026-11-15 after rejecting shift-tab and arrows for the list switch. `rvrs show` searches history, then saved runs. A run carries `source` (the address probes left from, read from a connected UDP socket) and `public_source` (RIPEstat's `whats-my-ip`, asked once per run when network lookups are on, remembered for five minutes in the process). Lists show both as SOURCE and PUBLIC; a pipe gets every column, a terminal drops them when narrow. Never print or commit a real public address in docs or tests: examples use 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 and AS64500.
- **Favorites and the filter.** `Favorites` (`favorites.json`, hosts as typed, newest first, compared without case) is the app's `FavoriteStore`: a favorite is a host, never a run. `rvrs favorite <host>`, `rvrs favorites`, and shell completion offers favorites before history. In the Console ⇧2 lists them (host, runs in history, newest run) and Return runs the selected tool against one; `f` toggles the host of a selected run, of a favorite, or of the hop whose details are open (the run's target when they are closed). A favorite is marked with a heart (the user's choice), behind the host in the hop details and the run's Target line, and in the lists; saved runs keep the star. The Target field is also the filter (the user asked for a typeahead over host and tool, 2026-11-15): every typed word must appear in a row's tool or host, the panel title shows the words, and Return with no row selected runs what is typed, where two words starting with a tool name pick the tool. Letters are shortcuts whenever a row is selected, so left or up returns to typing.
- **Hop details.** Return or right on a hop opens its details in a column beside the table (under it below 110 columns), never as a modal: the user wants to keep moving through the hops while the details follow. Order in the column: facts, latency, network, then actions (network above the actions is the user's call). Tab moves the keys between the two columns; the focused panel has the bright frame. In the details the arrows pick an action and Return does it; `t m p c n w` do the same from the hops (`Action::key`).
- **Leaving a live run.** `App::retire` stops a run that is still going when another is started or the Console quits, and keeps what it measured in history, so a long MTR is never thrown away.
- **Quitting.** Only the overview quits (esc on an empty field, or Ctrl-C anywhere). A run and a hop's details have no `q` (the user's call, 2026-11-15): left steps back out.
- **Console.** `console::App` holds the field, the selected tool (tab switches between the available ones), the list (Recent, Favorites or Cases, filtered by what is typed), the open case and the case picker, the shown run (live or saved) and the hop sheet. `console_run.rs` is the run picker (the user's ask, 2026-11-20): `r` on a run in a list or on the host a result's selection names (a hop, a record's host, a BGP network, prefix or address) opens every tool that can take that host (`tools_for`: an AS number or a prefix only BGP, an address no dig, a private address no BGP), and `R` runs the open run again. The tool chosen last is kept in `console.json` in the config directory, written by `open` whenever it changes, and `Tool::ALL` lists iperf3 last. An MTR charts latency, jitter (the move from one reply to the next) and loss (over a 10-round window) above the table, side by side from 120 columns, and in a hop's details (`mtr_charts`, `metric_chart`). `draw` is one panel: Recent (or suggestions) at the start, the run once one is open. Tests render to ratatui's `TestBackend` and assert on the text.

## Conventions

- Versions come from git (`crates/rvrs/build.rs`, the user's call, 2026-11-16, so a server always shows what it runs): `RVRS_VERSION` is `VERSION` (major.minor) plus the commits since `VERSION` last changed, one more for a dirty tree; `RVRS_COMMIT` is the short commit, `-dirty` when uncommitted. `help::VERSION` and `help::COMMIT` read them, and `rvrs --version` prints `rvrs 0.2.3 (4ea5d4e)`. Never set a version in `Cargo.toml` to change what people see; bump `VERSION` and commit it with a bigger change. Without git the crate's own version and "unknown" stand in.
- Stored types (`Run`, `Hop`, `Slot`, `Network`) are read back from `history.json` across versions. A new field carries `#[serde(default)]` and a test that an older file still loads, or the person's history is gone.
- The report is the iOS app's `RunReport`, field for field (`../ios-app/rvrs/Models/RunReport.swift`). Change both together. Its schema is written down in this repo, as JSON Schema with fixtures, before the API stores runs, and the API and the app mirror it (see Repositories).
- Statistics and sentences match the app: jitter is the mean step between consecutive replies, percentiles are nearest rank, summaries and interpretation are the app's strings. Port, don't reinvent.
- rvrs's own flags are long only, so they never collide with a tool's short flags.
- An unsupported flag is an error that names it. Never ignore a flag when ignoring it changes the result.
- Data goes to stdout. Errors go to stderr as `rvrs: <one sentence>`. Exit 0 for a run that was made, 1 for one that couldn't be, 2 for usage. ping keeps its own codes: 0 answered, 1 no reply, 2 couldn't run.
- Color is the terminal's sixteen colors plus bold and dim, so it follows the person's theme. The one exception is the logo at the Console's top right (`LOGO`, `LOGO_MASK`, `logo_lines`): the try shell's art in its own colors (the user's design, 2026-11-20), whole where the header has room, cut to the mark and the rules (`LOGO_CUT`) where it doesn't, hidden on a narrow terminal. Never state something by color alone. Green for a reached destination, yellow for no reply, red for errors, blue for data (bars, spinner).
- No call to a system network tool, ever. `pbcopy`, `wl-copy`, `xclip` and `open` are used for the clipboard and the browser only.
- Every string follows `.claude/skills/rvrs-voice/SKILL.md`, and every term `GLOSSARY.md`. Both are copies of the app's; edit there and copy.
- A networking change comes with a parsing or model test. A live trace against a public host is the integration check.
